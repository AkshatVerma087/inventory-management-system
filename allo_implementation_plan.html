Phase 1 Project Initialization & Environment ▾
1.1 Setup Critical
Scaffold the Next.js 14 project with App Router
Run create-next-app with TypeScript, Tailwind CSS, ESLint, App Router, and src-dir flags. This is the foundation everything else is built on.
Command to run
npx create-next-app@latest allo-inventory --typescript --tailwind --eslint --app --src-dir --import-alias "@/*"
Flags explained
  • --typescript: enables TypeScript throughout the project
  • --tailwind: installs Tailwind CSS and generates tailwind.config.ts
  • --app: uses the new App Router instead of legacy Pages Router
  • --src-dir: all source files live in src/ instead of the project root
  • --import-alias "@/*": allows importing from @/components instead of ../../components
Why App Router?
  • Server Components fetch data at render time — no useEffect data fetching needed on the listing page
  • API Routes and Server Components live in the same deployment unit on Vercel
  • Built-in support for streaming, React Suspense, and incremental static regeneration
1.2 Setup Critical
Install all backend dependencies
Install Prisma, Zod, Upstash Redis, Upstash rate limiter, and shadcn/ui peer dependencies in one shot.
Core packages
  • prisma + @prisma/client — ORM and type-safe query client
  • zod — schema validation, shared between API and frontend
  • @upstash/redis — HTTP-based Redis client for serverless environments
  • @upstash/ratelimit — rate limiting built on top of Upstash Redis
shadcn/ui peer deps (needed on Day 2)
  • @radix-ui/react-dialog, @radix-ui/react-slot — accessible primitive components
  • lucide-react — icon set used by shadcn
  • class-variance-authority, clsx, tailwind-merge — utility libraries for component variants
Dev dependencies
  • ts-node — needed to run the Prisma seed file with TypeScript
  • @hookform/resolvers — Zod adapter for React Hook Form (install on Day 2)
  • react-hook-form — form state manager (install on Day 2)
1.3 Setup Critical
Configure environment variables (.env.local)
Create .env.local immediately and add it to .gitignore before the first commit. Populate all required keys from Supabase and Upstash dashboards.
Required environment variables
  • DATABASE_URL — PostgreSQL connection string (use pooler URL from Supabase/Neon)
  • DIRECT_URL — direct connection URL for Prisma migrations (bypasses PgBouncer)
  • UPSTASH_REDIS_REST_URL — REST endpoint from the Upstash Redis dashboard
  • UPSTASH_REDIS_REST_TOKEN — auth token from the Upstash Redis dashboard
  • RESERVATION_TTL_SECONDS — set to 600 (10-minute reservation window)
  • CRON_SECRET — a random string to protect the expiry cron endpoint from public access
⚠ Add .env.local to .gitignore BEFORE making your first commit. One leaked credential in git history is permanent. DIRECT_URL must be separate from DATABASE_URL because Supabase's pooler (PgBouncer) blocks DDL statements required by Prisma migrations.
Also create .env.example
  • Duplicate .env.local with all keys but empty values
  • Commit .env.example to the repo so teammates know what variables are needed

Create the full folder structure
Manually create all directories: controllers/, services/, repositories/, lib/, schemas/, and types/. Empty folders signal the architecture to teammates immediately.
Folders to create under src/

  • services/ — business logic, one file per resource

Phase 2 Database Design & Prisma ▾
2.1 Database Critical
Provision a hosted PostgreSQL database
Create a free-tier project on Supabase or Neon. Copy both the pooler connection URL (for DATABASE_URL) and the direct connection URL (for DIRECT_URL) into your .env.local.
Why hosted Postgres (not local)?
  • The exercise explicitly requires a hosted database — not local or SQLite
  • SELECT FOR UPDATE NOWAIT is a PostgreSQL feature; SQLite does not support it
  • Supabase and Neon both have free tiers that are more than sufficient
  • The live Vercel deployment can connect to it immediately without extra config
Supabase setup steps
  • Go to supabase.com → New project → choose a region close to your Vercel region
  • Settings → Database → copy the URI under "Connection pooling" for DATABASE_URL
  • Settings → Database → copy the URI under "Direct connection" for DIRECT_URL
2.2 Database Critical
Initialise Prisma and write the schema
Run npx prisma init, then write the complete schema with all five models: Product, Warehouse, StockLevel, Reservation, and the ReservationStatus enum.
Models and key fields
  • Product: id (cuid), name, sku (unique), price (Decimal 10,2), imageUrl, description
  • Warehouse: id (cuid), name, location
  • StockLevel: productId, warehouseId, totalUnits, reservedUnits — unique([productId, warehouseId])
  • Reservation: id, productId, warehouseId, quantity, status (enum), expiresAt, idempotencyKey (nullable unique), confirmedAt, releasedAt
  • ReservationStatus enum: PENDING, CONFIRMED, RELEASED
Design decisions explained
  • reservedUnits column: availableUnits = totalUnits - reservedUnits avoids expensive COUNT queries on reservations
  • Decimal(10,2) for price: avoids floating-point errors on monetary values
  • idempotencyKey as nullable unique: costs nothing now, enables the bonus feature without a schema change later
  • confirmedAt / releasedAt timestamps: useful for analytics and debugging without extra queries
Required indexes
  • @@unique([productId, warehouseId]) on StockLevel — enforced at DB level, not just ORM
  • @@index([status, expiresAt]) on Reservation — cron expiry query filters on both; without this it's a full table scan
  • @@index([productId, warehouseId, status]) on Reservation — availability lookups during reservation creation
2.3 Database Critical
Run migration and generate Prisma client
Execute npx prisma migrate dev --name init to apply the schema to the database, then npx prisma generate to produce the typed client.
Commands in order
  • npx prisma migrate dev --name init — creates the SQL migration file and runs it against the dev database
  • npx prisma generate — generates /node_modules/.prisma/client with full TypeScript types
  • npx prisma studio — open in browser to visually verify the tables were created correctly
⚠ If Prisma can't connect, check that DATABASE_URL uses the direct connection URL, not the pooler, for migration. Supabase's pooler (PgBouncer) does not support the DDL statements Prisma needs.
2.4 Database High
Write and run the seed script
Create prisma/seed.ts to populate at least 2 warehouses, 3 products, and meaningful stock levels for each product-warehouse combination.
Seed data requirements for demo
  • At least 2 warehouses with different names and locations (e.g. Mumbai Hub, Delhi Hub)
  • At least 3 products with different prices and realistic names
  • StockLevel row for each product-warehouse pair with totalUnits >= 10 and reservedUnits = 0
  • Set one product to have low stock (totalUnits = 1) so the concurrency test is easy to demonstrate
Setup steps
  • Add to package.json: "prisma": {"seed": "ts-node prisma/seed.ts"}
  • Run: npx prisma db seed
  • Verify in Prisma Studio that all rows were created correctly
2.5 Database Critical
Create the Prisma singleton (lib/db.ts)
Create a single PrismaClient instance cached on the global object in development to prevent multiple instances during hot reload, which exhaust database connections.
Why a singleton?
  • Next.js dev server hot-reloads modules frequently. Without caching on global, each reload creates a new PrismaClient and opens a new connection pool
  • Supabase free tier has a connection limit; exhausting it causes "too many clients" errors
  • The pattern: check if globalThis.prisma exists, use it if so, otherwise create and store it
  • In production, modules are not hot-reloaded so the singleton pattern doesn't matter, but it doesn't hurt
File location
src/lib/db.ts

Phase 4 Repository Layer (All Database Queries) ▾
4.1 Repository High
Create product.repository.ts
Exports findAll() which fetches all products with their stock levels and warehouses included. Exports findById(). No business logic here — pure data access only.
Methods to implement
  • findAll(): queries db.product.findMany with include: {"{ stockLevels: { include: { warehouse: true } } }"}
  • findById(id: string): queries db.product.findUnique with the same includes
Architecture rule
Repositories are the ONLY files that import db from lib/db.ts. Services call repositories. Controllers call services. Routes call controllers. This chain must not be broken.
4.2 Repository High
Create warehouse.repository.ts
Simple repository with findAll() and findById(). Warehouse data is straightforward — no joins needed beyond the basic fields.
Methods to implement
  • findAll(): db.warehouse.findMany() — returns all warehouses
  • findById(id: string): db.warehouse.findUnique({ where: { id } })
4.3 Repository Critical
Create stock.repository.ts with row-level locking
This is the most critical repository. It must use a raw SQL query with SELECT FOR UPDATE NOWAIT to acquire a row-level lock. Also implements incrementReserved and decrementReserved for atomic stock mutations.
Methods to implement
  • findWithLock(productId, warehouseId): raw SQL SELECT with FOR UPDATE NOWAIT — locks the row against concurrent writes
  • incrementReserved(productId, warehouseId, qty, tx): called inside a Prisma $transaction — adds qty to reservedUnits
  • decrementReserved(productId, warehouseId, qty, tx): called inside a Prisma $transaction — subtracts qty from reservedUnits
  • decrementTotal(productId, warehouseId, qty, tx): called on confirm — permanently reduces totalUnits
⚠ Prisma's fluent API does not support SELECT FOR UPDATE. The findWithLock method MUST use db.$queryRaw. This is the intentional and necessary exception to the ORM abstraction. NOWAIT means the query fails immediately if the row is locked rather than waiting, which is critical for the race condition guarantee.
Why these two separate methods (increment vs decrementTotal)?
  • On reserve: only reservedUnits increases (totalUnits unchanged)
  • On confirm: both totalUnits AND reservedUnits decrease (net effect: reservation becomes permanent stock removal)
  • On cancel/release: only reservedUnits decreases (totalUnits unchanged, units go back to available)
4.4 Repository Critical
Create reservation.repository.ts
Full CRUD for reservations including create, findById (with product and warehouse relations), updateStatus, and findExpiredPending for the cron job.
Methods to implement
  • create(data, tx): creates a Reservation row inside a Prisma transaction
  • findById(id): findUnique with product and warehouse relations included
  • findByIdempotencyKey(key): used in the bonus feature to check for duplicate requests
  • updateStatus(id, status, timestamp, tx): updates status to CONFIRMED or RELEASED, sets confirmedAt or releasedAt
  • findExpiredPending(): findMany where status = PENDING AND expiresAt < new Date() — used by the cron job
Phase 5 Service Layer (Business Logic) ▾
5.1 Service High
Create product.service.ts
Calls the product repository, then maps over the results to compute and attach availableUnits (totalUnits minus reservedUnits) to each stock level row.
Business logic to implement
  • Call productRepository.findAll()
  • Map each product's stockLevels to add availableUnits = totalUnits - reservedUnits
  • Optionally filter out stock levels where totalUnits = 0 (no stock at all at that warehouse)
  • Return the enriched ProductWithStock array
5.2 Service Critical
Create reservation.service.ts — createReservation()
The core of the exercise. Orchestrates: check idempotency cache → acquire Redis lock → run Postgres FOR UPDATE → check availability → create reservation + increment stock in a single transaction → release lock.
Step-by-step flow
  • Step 1: If an idempotencyKey is provided, check Redis for a cached response. If found, return it immediately without any DB access.
  • Step 2: Call withLock(productId:warehouseId) from lib/lock.ts to acquire the Redis distributed lock. If it returns null, return a conflict error to the caller.
  • Step 3: Inside the lock callback, call stockRepository.findWithLock(productId, warehouseId) to acquire the Postgres row lock. This is the true concurrency guarantee.
  • Step 4: Calculate available = totalUnits - reservedUnits. If available < quantity, return an insufficient stock signal.
  • Step 5: Open a Prisma $transaction. Inside it: call reservationRepository.create() and stockRepository.incrementReserved(). Both must succeed or both roll back.
  • Step 6: The withLock finally block automatically releases the Redis lock.
  • Step 7: If idempotencyKey was provided and the reservation succeeded, store the response in Redis with a 24-hour TTL.
⚠ The Redis lock and the Postgres FOR UPDATE lock must both be used. Redis prevents thundering herd (many requests all reaching the DB simultaneously). Postgres ensures correctness even if the Redis lock fails or expires. Belt and suspenders.
5.3 Service Critical
Create reservation.service.ts — confirmReservation()
Fetches the reservation, checks it is PENDING and not expired (returning a 410 signal if expired), then runs a transaction to set status to CONFIRMED and permanently decrement both totalUnits and reservedUnits.
Step-by-step flow
  • Step 1: Fetch the reservation by id using reservationRepository.findById()
  • Step 2: If not found, return a not-found signal (caller returns 404)
  • Step 3: If status !== PENDING OR expiresAt < new Date(): this reservation is expired. If it is still PENDING, release the stock as a cleanup step. Return an expired signal (caller returns 410).
  • Step 4: Open a Prisma $transaction. Inside: updateStatus to CONFIRMED, and call stockRepository.decrementReserved AND stockRepository.decrementTotal with the reservation's quantity. This permanently removes the units from inventory.
5.4 Service Critical
Create reservation.service.ts — releaseReservation() and releaseExpired()
releaseReservation() handles user-initiated cancel. releaseExpired() is called by the cron job to batch-release all expired PENDING reservations.
releaseReservation() flow
  • Fetch reservation. If not found or not PENDING, return an error signal.
  • Open a transaction: updateStatus to RELEASED, call stockRepository.decrementReserved. totalUnits is NOT decremented — units return to available.
releaseExpired() flow (for cron)
  • Call reservationRepository.findExpiredPending() to get all PENDING reservations past their expiresAt
  • Loop over each and open a transaction: updateStatus to RELEASED, decrementReserved
  • Return the count of released reservations for logging
Phase 6 Controller Layer (HTTP In / Out) ▾
6.1 Controller High
Create product.controller.ts and warehouse.controller.ts
Each exports a list() method that calls the corresponding service, then formats the result as a NextResponse JSON. No business logic — only HTTP in, service call, HTTP out.
Controller responsibilities
  • Parse query parameters or route params from the NextRequest object
  • Validate inputs using Zod (safeParse, not parse — so you can return 400 instead of throwing)
  • Call the appropriate service method
  • Map service return values to HTTP status codes and JSON bodies
  • Controllers must never throw — all errors are caught and returned as NextResponse
6.2 Controller Critical
Create reservation.controller.ts — create()
Parses and validates the request body with CreateReservationSchema. Extracts the Idempotency-Key header. Calls reservationService.createReservation(). Maps service results to 201, 400, or 409 responses.
HTTP status codes to return
  • 201 Created — reservation successfully created
  • 400 Bad Request — Zod validation failed (invalid body shape)
  • 409 Conflict — insufficient stock OR Redis lock could not be acquired (another request is in progress)
Idempotency-Key handling
  • Extract header: req.headers.get('Idempotency-Key')
  • Pass it to the service. The service checks Redis and either returns cached response or runs the full flow.
  • On retry (cache hit): return the original 201 response — same body, same status, no side effects
6.3 Controller Critical
Create reservation.controller.ts — confirm() and release()
Both methods validate the :id route param, call the service, and map service signals to 200, 404, 410, or 400 responses.
confirm() status codes
  • 200 OK — reservation confirmed successfully
  • 404 Not Found — reservation ID does not exist
  • 410 Gone — reservation has expired (payment window passed)
release() status codes
  • 200 OK — reservation released successfully
  • 404 Not Found — reservation ID does not exist
  • 400 Bad Request — reservation is not in PENDING state (already confirmed or released)

Phase 8 Redis Setup & Distributed Lock ▾
8.1 Redis Critical
Provision Upstash Redis and create lib/redis.ts
Create a free Redis database on upstash.com. Copy the REST URL and token into .env.local. Create lib/redis.ts that exports a single Redis instance using Redis.fromEnv().
Why Upstash (not standard Redis)?
  • Standard Redis clients use persistent TCP connections. Serverless functions (Vercel) are stateless and short-lived — they cannot maintain persistent connections.
  • Upstash provides Redis over HTTP REST. Each call is a single HTTP request — perfect for serverless.
  • Redis.fromEnv() automatically reads UPSTASH_REDIS_REST_URL and UPSTASH_REDIS_REST_TOKEN — no manual config.
8.2 Redis Critical
Implement withLock() in lib/lock.ts
Implement acquireLock (SET key 1 NX PX 5000), releaseLock (DEL key), and withLock(key, fn) wrapper that automatically releases in a finally block.
Lock mechanics
  • NX (Not eXists): the SET command only succeeds if the key does not already exist — atomic check-and-set
  • PX 5000: the lock auto-expires after 5 seconds even if the process crashes before releaseLock is called
  • If SET returns OK: lock acquired. If it returns null: another process holds the lock — return null to caller.
  • withLock wraps the callback in try/finally to guarantee lock release even if the callback throws
  • Lock key format: lock:{productId}:{warehouseId} — one lock per product-warehouse combination

10.4 UI Critical
Build CountdownTimer (Client Component)
A 'use client' component that accepts expiresAt (ISO string) and status. Uses setInterval in useEffect to tick every second. Turns red and pulses when under 60 seconds. Clears the interval on unmount.
Implementation details
  • remaining = max(0, new Date(expiresAt).getTime() - Date.now())
  • Recompute every second via setInterval
  • Format as MM:SS — minutes Math.floor(remaining / 60000), seconds Math.floor((remaining % 60000) / 1000).toString().padStart(2, '0')
  • When remaining < 60000: apply red colour and animate-pulse CSS class
  • When remaining = 0 OR status is not PENDING: stop interval and show "Expired" message
  • Return () => clearInterval(interval) from useEffect to prevent memory leaks on unmount
File location
src/components/reservations/CountdownTimer.tsx
10.5 UI Critical
Build ReservationActions (Client Component)
Confirm and Cancel buttons. On click: POST to the appropriate API endpoint, handle 410 with a toast error, call router.refresh() on success so the Server Component re-fetches and the UI updates without a full page reload.
Button behaviour
  • If status !== PENDING: render a read-only status message instead of buttons
  • Track loading state: 'confirm' | 'cancel' | null — disable both buttons while any action is in flight
  • On confirm: POST /api/reservations/{id}/confirm. If 410: toast "Reservation expired". If 200: toast "Purchase confirmed!" + router.refresh()
  • On cancel: POST /api/reservations/{id}/release. If 200: toast "Reservation cancelled" + router.refresh()
  • router.refresh() re-runs the Server Component tree, fetching fresh reservation data from the database and re-rendering the page with the new status

src/components/reservations/ReservationActions.tsx
